One Spec Design

Design note · state-example · 12 Nov 2026

One spec, proved software

A way to turn user stories into formally verified TypeScript with one hand-written source of truth, and what building it on a toy and on a larger, synthesized example showed.

You write one Markdown file per application: its stories, the rules each story implies, and under every rule the few lines of Quint that say the same thing exactly. A tool derives everything else: a Quint model that is simulated, a TypeScript module of types, guards and transitions, and proofs, by LemmaScript and Dafny, that every transition preserves every rule. The agent working in your session keeps the stories, rules and model in step, and you sign off.

The toy is an order checkout: 253 lines of Markdown give 10 transitions and 10 rules, all proved. The larger example is a synthesized team task dashboard modelled in about 700 lines of spec. The tooling is about 1,400 lines of TypeScript in two files.

The design in one picture

Why this shape

The request names five embodiments of the same truth: stories, rules, an ontology, state models and code. Each pair that is maintained separately needs a diff and a sync, so the design question is how few can be hand-written.

  1. Prose and formal text cannot be derived from each other, only compared. So the two halves of a rule sit next to each other in one file, and the tool tracks whether anyone has compared them since either changed. Adjacency replaces IDs.
  2. A deterministic transition is its own contract. If the model says what pay returns, the strongest postcondition for a hand-written pay is that same expression. So transitions are generated, and hand-written code starts where Quint stops.
  3. Simulation and proof find different mistakes. Simulation gives a trace in milliseconds but only samples. Proof covers every state but gives no trace. Run on the same definitions, they are complementary.

Writing a spec

A ## heading is a story, a ### heading is a rule, and the quint block under a rule is its formal half. There are no state variables and no actions: only types and pure definitions, whose role comes from their name.

spec/order.md, written by hand 
## Story: Check out

> As a shopper, I want to submit my order and pay
> it off in one or more payments, so that I do not
> need the whole amount at once.

### A payment never exceeds the balance

A payment is a positive amount toward a pending
order. The payment that clears the balance marks
the order as paid.

```quint
pure def canPay(o: Order, amount: int): bool =
  o.status == Pending and amount > 0
    and o.paid + amount <= o.due

pure def pay(o: Order, amount: int): Order =
  val paid = o.paid + amount
  { ...o, paid: paid,
    status: if (paid == o.due) Paid else Pending }
```

### A pending order still has a balance

```quint
pure def alwaysPendingHasBalance(o: Order): bool =
  o.status == Pending implies o.paid < o.due
```
gen/order.ts, generated 
/** Story: Check out / A payment never exceeds
    the balance (spec/order.md:73) */
//@ pure
export function canPay(o: Order, amount: number): boolean {
  return o.status === "Pending" && amount > 0
    && o.paid + amount <= o.due;
}

//@ pure
export function pay(o: Order, amount: number): Order {
  //@ ensures (inv(o) && canPay(o, amount))
  //@   ==> alwaysPendingHasBalance(\result)
  // … one such line for every rule
  const paid = o.paid + amount;
  return { ...o, paid: paid,
    status: paid === o.due ? "Paid" : "Pending" };
}

You writeIt means
pure val initial: OrderThe initial state. Its type is the state type. A spec without one is a library.
pure def pay(o: Order, …): OrderA transition, and an event the application can send.
pure def canPay(o: Order, …): boolThe guard of pay.
pure def alwaysX(o: Order): boolHolds in every reachable state.
pure def stepX(before: Order, after: Order): boolHolds across every single transition.
pure def sometimesX(o: Order): boolSome reachable state satisfies it.
pure def lawX(…): boolTrue for every value of its parameters.
pure val idValues = Set(1, 2, 3)What the simulator tries for a parameter named id.

Four mechanisms do most of the ergonomic work. Tangling keeps every line on its own line number, so a Quint error is reported as spec/order.md:78:51. The state variable, one action per transition and the invariants are generated, so a transition cannot be left out of the simulation. Every generated export carries a doc comment naming its story, rule and spec line. And because the proofs assume whole numbers and plain data, the module exports parseEvent, which turns an untrusted value into an event or nothing: it checks the shape and that every number is a safe integer, and returns a fresh copy with exactly the event's fields, so nothing the caller keeps can change it afterwards.

What data a spec can describe

In a specIn TypeScriptWorth knowing
int, bool, str, recordsnumber, boolean, string, interfacesRecords nest. / and % go towards zero, as in Quint, exactly, including for negative numbers.
type Status = Draft | Paid"Draft" | "Paid"
type Parcel = Packed({ weight: int }) | Lost{ tag: "Packed"; weight: number } | { tag: "Lost" }Each stage carries only what is known at that stage. Read with match.
List[T]T[]append, concat, select, foldl, nth, every, some, includes, listMap. A table is a list of records.
Set[T] of simple valuesT[] that never holds a value twiceUse a set only when duplicates are impossible in the real thing.
str -> TRecord<string, T>Lookup, update and "is this key present". A map cannot be iterated. Keys are stored with a $ in front, so none can collide with a property every object has.

Three rules of thumb follow from what can be proved. Guard every partial operation in the definition that uses it: an index outside a list, a missing map key or a zero divisor stops the simulator and cannot be proved safe, so test first and return a default. There are no loops and no recursion in Quint: to repeat something until done, fold over a list that is long enough; what needs a real loop is written by hand in src/ and proved there. Keep simulation bounds out of guards, because a guard is shipped code.

What is checked, and how strongly

npm run check runs these stages cheapest first. A broken model stops the later stages, since their failures would only restate the first.

StageQuestionStrength
modelIs the spec well-typed and inside the supported subset?exact; anything unsupported is refused by name
alwaysDoes a reachable state break an always rule, a step break a step rule, or a sampled argument break a law?sampled 10,000 traces; a failure comes with the shortest trace
sometimesCan each goal be reached at all?a witness trace is a proof
replayDoes the generated TypeScript mean what the Quint means?sampled 400 traces: every state, every law tried, and every definition the simulator can evaluate, compared result by result; the ones it cannot evaluate are listed
typesDoes the application fit the generated contract?exact
proofDoes every transition preserve every rule, does every law hold, and does hand-written code meet its annotations?proved for all states and inputs; what Dafny cannot prove alone is listed
testsDoes the shell work?examples
reviewDoes every story have rules, and has every rule that changed been reconciled?tracked

When a proof does not go through

Dafny proves arithmetic and simple list facts unaided. It usually cannot prove a rule that depends on a fold or a count. When proof lists an obligation as "not proved" although simulation found nothing, there are four answers: state the missing fact as another rule; move the arithmetic into a small function with a law; write it by hand with loop invariants; or accept simulation for it. The last is a person's decision, recorded with npm run accept -- unproved in a ledger, spec/unproved.lock.json. The check then reports how many obligations are simulated only, and fails again if a new one appears.

Keeping stories, rules and model in step

The check detects; the agent working in the session translates. That agent, Claude Code or any other that reads AGENTS.md, follows a skill kept in the repository, .claude/skills/sync/SKILL.md. It runs npm run check, which reports what is out of step together with both halves of every rule that moved, makes each translation, and repeats until only a person's sign-off is left. Nothing else has to be installed or signed in.

The report saysDirectionThe agent
story has no rulesstory → ruleswrites one rule per thing the story requires, then each rule's Quint
not formalizedrule → modelwrites Quint that says exactly what the sentence says
prose changedrule → modelchanges the Quint if the meaning moved
model changedmodel → rulerewrites the sentence so a reader of the prose alone is not misled
a trace breaks a rulemodel → rulewrites the reason as a new rule and guard, marked "Discovered by simulation"
an obligation is not provedmodel → rulelooks for an unstated fact about reachable states and adds it, marked "Discovered by the proof"
removed or renamedchecks that no story still depends on the rule

Each rule has two fingerprints, one for its prose and one for its Quint, stored when a person runs npm run accept. That is how the report knows which half moved. accept runs the whole check afresh, ignoring anything remembered from earlier runs, and records nothing unless every other stage passes. The agent never runs it. A model element with no rule cannot exist, because Quint is only read from blocks under a rule heading.

One sync, start to finish

Two things were changed by hand, as a person would: a story was added in prose only (staff can put a pending order on hold while stock is checked, and release it), and a constant was changed in the Quint.

The story became three rules: staff can hold and release a pending order; nothing is paid while it is on hold, which is a rule about each step; and an order can be on hold. Simulation passed, but the proof could not show that releasing an order leaves it with a balance, because nothing said that an order on hold is unpaid. That became a fourth rule, "An order on hold still has a balance". The five items left are the person's to accept.

The two ways a rule is discovered

Simulation finds a missing guard and shows the shortest way to the problem, then proposes the bluntest possible repair:

✗ always    a reachable state breaks "Story: Check out / A pending order still
            has a balance" (spec/order.md:93)
      initial                        -> {"due":0,"paid":0,"status":"Draft","units":0}
      {"type":"submit"}              -> {"due":0,"paid":0,"status":"Pending","units":0}
      the last event is "Story: Check out / Only a non-empty draft can be submitted"
      (spec/order.md:63); its guard canSubmit let it through
      if no better reason can be found: refuse submit when its result would break alwaysPendingHasBalance

The agent should state the reason ("only a non-empty draft can be submitted"). The last line is a fallback that is always sound and never insightful. It is expressible because a guard may call its own transition to look at the result.

The proof finds an unstated assumption. Delete the rule "Drafts and cancelled orders hold no money" and 10,000 traces still pass, because no trace ever puts money on a draft. The proof does not pass: Dafny considers a draft that already has its full amount paid, which nothing forbids. The rules were true but not inductive, and stating the missing fact is the fix.

Composing specs

  • A library is a spec with no state: definitions and laws. Others take its names as they are with import kernel.* from "./kernel".
  • Any spec, a state machine included, can be imported under a name. With import lamp as L from "./lamp", a room holds two lamps in its state, moves them with L::toggle, requires L::alwaysFlipsAreCounted of each, and adds rules about the pair that neither lamp could state. This is how one machine uses and observes another.
  • Each spec is proved against the definitions of what it imports, not their proofs, so the cost of a proof grows with the spec and not with everything beneath it.
  • Only what changed is checked again. A spec that passed simulation, and each proof result, is remembered under a fingerprint of the spec, everything it imports and the versions of the tools. A repeat check of an unchanged three-spec project takes about two seconds.
  • The toolchain is a package with a spec command. In another repository, npx spec init adds the sync skill, AGENTS.md, a tsconfig and package scripts, replacing nothing, and npm run check runs the pipeline.

Hand-written logic that Quint cannot express, such as a loop over an event log, is ordinary TypeScript in src/ with LemmaScript annotations. It imports one generated module and is proved in a bundle with it, in a directory of its own with its own prover configuration. Annotations that tell the prover to trust or skip something are refused wherever they appear.

A larger example

To see what a less tidy application needs, the same tools were pointed at a synthesized one, modelled on a common kind of application: a team task dashboard whose tasks live in a shared spreadsheet that people also edit by hand, with a chat app for commands and notifications and a web dashboard for viewing. Its names and data are made up. It is modelled in examples/dashboard, a separate package that depends on the toolchain as any project would.

SpecKindCovers
kernel.mdlibrary, 10 lawsThe number a new row gets, when an edit is announced, which reminder is due, paging, request freshness
tracker.mdmachine, 20 transitionsOne sheet: guarded dashboard edits, unguarded hand edits, the warning list and its fixes, notifications
projects.mdmachine, 4 transitionsThe project list: one sheet per project, one project per channel, never guessing
src/columns.tshand-written, provedColumn letters, which need a loop

Chat, HTTP, storage and the web dashboard are not modelled; they are the shell around these rules, and the example includes a small hand-written piece of it, src/notify.ts, which turns the model's notes into chat messages. Two kinds of writer, the guarded dashboard and a person typing in the sheet, needed no feature of their own: both are transitions, and a field in the state says who wrote last, so a step rule can say "a dashboard edit never adds a problem".

What the checks found

A name typed twice is notified twice. A natural first model keeps a task's owners in a set. A cell in a spreadsheet is not a set: a person can type ana, ana. With cells modelled as lists, the rule "nothing is sent twice" failed in simulation within seconds: removing duplicates when a cell is written is not enough if the notifier does not also remove them when it reads one. A set-based model cannot express that case. The spec now has the rule "A person named twice in a cell is told once", and the example's shell, src/notify.ts, sends each person one message; its test types a name twice and checks that the person is told once.

A flaw in Quint. A Quint definition that takes a lambda gives the wrong answer, silently, when used inside its own argument, as in tasks.some(t => t.parents.some(…)). So every, some, includes and listMap are not Quint definitions: the tool rewrites them into Quint's built-in fold before Quint sees the spec, and they come out in TypeScript as native array methods.

A flaw in the generator. Quint divides towards zero; the generator floored. Sampled laws had not hit a negative dividend. Division and remainder now go through helpers that are exact in Quint, TypeScript and Dafny, and one law that had been unprovable proved once the translation was right.

A bounded model generates bounded code. A model that finds a task's ancestors with a fixed number of rounds of unrolling, say four, is enough for four tasks and wrong for a fifth, and the code generated from it inherits the bound. Here the search folds over the task list, so it runs once per task however many there are.

How much is proved

Everything holds in simulation. Not every obligation is proved for all inputs; those that hold only in simulation are listed in the example's spec/unproved.lock.json, and every run of its check counts them.

What this says about 500,000 lines

The specs state the rules of the dashboard in about 700 lines, because chat, HTTP and storage are not rules. A large codebase would be many such specs, one per area with a life cycle, with libraries beneath them and machines importing machines. What that needs from the tools is in place: dependency order, per-spec proof cost, incremental checking, and assurance reported per obligation. What has not happened is anyone trying it at that size. The largest thing these tools have modelled is the example above.

Limits

  • The generator is tested, not proved. Replay compares TypeScript with Quint on every state, law and definition that 200 sampled traces touch. A definition whose arguments the simulator cannot supply is compared only where events use it. Nothing short of proving the translator would close this.
  • Many obligations of a larger model are simulated, not proved. The ledger makes that visible and stops it growing unnoticed. Making it smaller means hand-written proofs.
  • The Quint subset is a subset. A map cannot be iterated, sets hold simple values only, and there is no recursion because Quint has none. Anything outside the subset is refused by name, never approximated.
  • Simulation samples. Event parameters are tried from −1 to 6 unless the spec says otherwise. The proof covers all values where it succeeds; quint verify can check a model exhaustively to a depth.
  • Agreement of prose and Quint is a judgement. The ledger records that the comparison was made. A rule that is wrong in both halves in the same way passes every check.
  • Numbers are JavaScript numbers. parseEvent admits only safe integers, but sums of them can pass 2^53, where the proofs' integers and JavaScript's part ways.
  • The working directory is trusted. Anyone who can edit the generated files, the cache or the tools can make a check say what they like. accept ignores the cache, and continuous integration should too.
  • Concurrency and time are where Quint is strongest and this profile does not use it: every spec is one sequential state machine.
