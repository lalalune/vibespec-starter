One Spec Design

Design note · state-example · 11 Nov 2026

One spec, proved software

How user stories become formally verified TypeScript with one hand-written file, what alternatives were weighed, and what a working toy shows about the approach.

The goal was a system where stories, rules, formal models and code are different views of one truth, kept in step, with as little to maintain as possible. The result is a 204-line Markdown file that holds an order-checkout application's stories, rules and Quint model, and about 1,200 lines of tooling that turn it into a TypeScript module whose every transition is proved, by Dafny, to preserve every rule. The pipeline runs in about 15 seconds on a quiet machine.

The design in one picture

Approaches considered

The request names five embodiments of the same truth: stories, rules, an ontology, state models and code. Each pair that is maintained separately needs a diff and a sync. The design question is how few of them can be hand-written.

ApproachHand-written sourcesWhat goes wrongVerdict
A. Layered documents
stories.md, rules.md, model.qnt, contract types, logic, linked by IDs		5Four sync problems. ID bookkeeping is busywork, and an LLM regenerating one layer from another is not repeatable.Rejected
B. Custom DSL
one YAML or JSON machine definition that emits Quint, TypeScript and docs		1You maintain a language. Guards and invariants end up as strings of some other language inside YAML.Rejected
C. TypeScript only
domain.ts with LemmaScript; XState-style machine		2No traces: a failed proof says what is unprovable, not how to get there. No reachability, so rules that forbid everything pass. Stories live elsewhere.Good, but mute on design errors
D. Quint model + hand-written TypeScript
types generated, transition bodies written by hand and proved		3Every transition is written twice, in Quint and in TypeScript, and kept equal by tests. For a deterministic rule the contract and the body are the same expression.Rejected for the core, kept for the edges
E. One literate spec
Markdown with Quint under each rule; everything else generated		1The generator supports a subset of Quint and must be trusted or tested.chosen

Three observations settled it.

  1. Prose and formal text cannot be derived from each other, only compared. Translating a sentence into Quint is a judgement. So the cheapest arrangement is to put the two halves of a rule next to each other in one file and track whether someone has compared them since either changed. Adjacency replaces IDs.
  2. A deterministic transition is its own contract. If the model says pay returns { ...o, paid: o.paid + amount }, the strongest postcondition for a hand-written pay is that same expression. Writing it twice adds a sync problem and no information. So the transitions are generated too, and hand-written code starts where Quint stops.
  3. Simulation and proof find different mistakes. Quint gives a trace in milliseconds but only samples. Dafny covers every state but gives no trace. Used on the same definitions they are complementary, and the second one costs nothing extra to set up because the TypeScript it needs is generated.

What a rule looks like

A spec is Markdown. A ## heading is a story, a ### heading is a rule, and the quint block under a rule is its formal half. There is no state variable and no action in the spec: only types and pure definitions. The role of each definition comes from its name.

You writeIt means
pure val initial: OrderThe initial state. Its type is the state type.
pure def pay(o: Order, …): OrderA transition, and an event the application can send.
pure def canPay(o: Order, …): boolThe guard of pay.
pure def alwaysX(o: Order): boolHolds in every reachable state.
pure def sometimesX(o: Order): boolSome reachable state satisfies it.
spec/order.md, written by hand 
## Story: Check out

> As a shopper, I want to submit my order and pay
> it off in one or more payments, so that I do not
> need the whole amount at once.

### A payment never exceeds the balance

A payment is a positive amount toward a pending
order. The payment that clears the balance marks
the order as paid.

```quint
pure def canPay(o: Order, amount: int): bool =
  o.status == Pending and amount > 0
    and o.paid + amount <= o.due

pure def pay(o: Order, amount: int): Order =
  val paid = o.paid + amount
  { ...o, paid: paid,
    status: if (paid == o.due) Paid else Pending }
```

### A pending order still has a balance

```quint
pure def alwaysPendingHasBalance(o: Order): bool =
  o.status == Pending implies o.paid < o.due
```
gen/order.ts, generated 
/** Story: Check out / A payment never exceeds
    the balance (spec/order.md:71) */
//@ pure
export function canPay(o: Order, amount: number): boolean {
  return o.status === "Pending" && amount > 0
    && o.paid + amount <= o.due;
}

//@ pure
export function pay(o: Order, amount: number): Order {
  //@ requires inv(o) && canPay(o, amount)
  //@ ensures alwaysDueMatchesUnits(\result)
  //@ ensures alwaysPaidWithinDue(\result)
  //@ ensures alwaysPendingHasBalance(\result)
  //@ ensures alwaysPaidInFull(\result)
  //@ ensures alwaysNoMoneyHeldOutsideCheckout(\result)
  const paid = o.paid + amount;
  return { ...o, paid: paid,
    status: paid === o.due ? "Paid" : "Pending" };
}

export type Event =
  | { type: "addItem"; qty: number }
  | { type: "submit" }
  | { type: "pay"; amount: number }
  | { type: "cancel" }
  | { type: "removeItem"; qty: number };
export function enabled(s: Order, e: Event): boolean
export function step(s: Order, e: Event): Order

The //@ lines are LemmaScript annotations. Dafny proves each one: starting from any order that satisfies every rule, a permitted payment of any amount leaves an order that satisfies every rule. One ensures per rule means a failed proof names the rule a transition breaks.

Three small mechanisms do most of the ergonomic work:

  • Line-preserving tangle. The Markdown becomes Quint by turning every non-code line into a comment on the same line number. A Quint error is reported as spec/order.md:78:51.
  • Generated harness. The state variable, one action per transition, step, and the invariant are generated, so a transition cannot be left out of the simulation and trace events line up with the TypeScript Event type by construction.
  • Doc comments carry the rule. Hovering pay in an editor shows its story, rule and spec line.
  • A generated gate for untrusted input. The proofs treat number as an integer, so the module also exports isEvent(x: unknown), which checks an incoming value's shape and that every number is a safe integer before the rules see it.

Keeping prose and model in step

Each rule has two fingerprints, one for its prose and one for its Quint, stored in spec/order.lock.json when someone runs npm run accept. The review stage compares the current fingerprints with the stored ones and says which way each rule moved.

StatusMeaningWho acts
not formalizedA rule was added in prose only.Agent writes the Quint, then the checks run.
prose changedThe sentence was edited, the Quint was not.Agent updates the Quint if the meaning moved.
model changedThe Quint was edited, the sentence was not.Agent rewrites the sentence if the meaning moved.
both changed / newBoth halves moved, or the rule is new.Agent or person confirms they agree.
removed or renamedA reconciled rule is no longer in the spec.Agent or person confirms it is meant to be gone.

npm run accept runs the whole check and records the listed rules only if every other stage passes, so a rule cannot be marked reconciled while its model is broken.

A model element with no rule cannot exist, because Quint is only read from blocks under a rule heading. That makes the sync structural in one direction and tracked in the other, with no IDs to maintain.

One session, both directions

The check detects; the agent working in the session translates. That agent, Claude Code or any other that reads AGENTS.md, follows a skill kept in the repository, .claude/skills/sync/SKILL.md. It runs npm run brief, which checks everything and prints what is out of step, makes each translation, and repeats until only a person's sign-off is left. A story with no rules becomes rules. A rule with no Quint gets its Quint. A rule whose model moved gets its prose updated, and the reverse. A counterexample or an unprovable transition becomes a new rule marked as discovered. Nothing else has to be installed or signed in, and the agent never accepts on the person's behalf.

An earlier design had the tool start an agent as a separate program. That made syncing depend on a second signed-in tool, which it should not. That command, npm run sync, remains for unattended use only.

How the checks discover rules

The session above shows a rule being discovered as it happens. Others among the nineteen rules in the example are of the same kind. Removing either one shows how each verifier finds its own sort of gap, and both removals are kept as regression tests of the pipeline.

Simulation finds a missing guard

With canSubmit written as "the order is a draft", the run takes under a second and prints the shortest way to the problem:

✗ always    a reachable state breaks "Story: Check out / A pending order still
            has a balance" (spec/order.md:91): fix the model, or add the rule
            that forbids this trace
      initial                        -> {"due":0,"paid":0,"status":"Draft","units":0}
      {"type":"submit"}              -> {"due":0,"paid":0,"status":"Pending","units":0}

An empty order can be submitted and then can never be paid. The fix is a rule a product owner would recognise, "Only a non-empty draft can be submitted", and one more conjunct in the guard.

Proof finds an unstated assumption

Remove the rule "Drafts and cancelled orders hold no money" and 10,000 simulated traces still pass, because no trace ever puts money on a draft. The proof does not pass:

✓ always    no rule broken in 10000 simulated traces
✓ replay    generated TypeScript reproduces 52 Quint traces
✗ proof     order.ts: not proved (full output in gen/proof/order.log)
      alwaysPendingHasBalance(submit(o))

Dafny considers a draft that already has its full amount paid. Nothing in the remaining rules says that cannot happen, and submitting it would produce a pending order with no balance. The rules were true but not inductive. Stating the missing fact as a rule fixes the proof and documents something the stories took for granted.

Hand-written logic and the trust boundary

Logic that fits in Quint belongs in the spec. What does not fit, such as a loop over an event log, is written in TypeScript against the generated contract and proved the same way:

export function replay(events: Event[]): Order {
  //@ ensures inv(\result)
  let order: Order = initial;
  let i = 0;
  while (i < events.length) {
    //@ invariant 0 <= i && i <= events.length
    //@ invariant inv(order)
    order = step(order, events[i]);
    i = i + 1;
  }
  return order;
}

LemmaScript verifies one file at a time and does not carry definitions across imports, so the pipeline proves such a file in a bundle with the generated module it imports. At run time the import is an ordinary import.

From the toy to a real application

The order example has four integers. To see what a real application needs, the same tools were pointed at one: a project tracker of about 5,500 lines whose data lives in hand-editable Google Sheets and which is used from Slack. It already had hand-written Quint models and a small proved kernel, so its rules were known. It is modelled in examples/alpha-energy as three specs, about 700 lines.

What the checks found

A real bug in the application. The application's own model keeps a task's owners in a set. A cell in a sheet is not a set: a person can type Liza, Liza. With cells modelled as lists, the rule "nothing is sent twice" failed in simulation within seconds:

✗ always    a reachable state breaks "Story: Be told what changed and what is due /
            Nothing is sent twice" (spec/tracker.md:435)
      …
      {"type":"renameOwner","owner":"wes","name":"liza"} -> … "owners":["liza","liza"] …
      {"type":"notify"} -> "sent":[{"kind":"Soon","task":1,"to":"liza","version":3},
                                   {"kind":"Soon","task":1,"to":"liza","version":3}]

That first trace was partly my model's fault: the application removes duplicates whenever it writes a cell, and my rename did not. But the application's notifier does not remove them when it reads a cell. I ran the application's own notifier, unmodified, on a task whose owners cell was typed as Liza Horowitz, Liza Horowitz, and it planned messages to ["U1","U1"]: the same person twice. The spec now carries the rule "A person named twice in a cell is told once", marked as discovered. The application itself was not changed.

A flaw in Quint itself. A Quint definition that takes a lambda gives the wrong answer, silently, when it is used inside its own argument, as in tasks.some(t => t.parents.some(…)). Both of Quint's evaluators do it. My first design defined the list helpers that way, and the simulator stopped with an error that led to a small reproduction. The helpers are now rewritten into Quint's built-in foldl before Quint sees the spec, and come out in TypeScript as native array methods.

Smaller things, each now a rule of thumb in CONTRIBUTING.md.

  • List access must be total. The lookup behind the one-click fix now tests its index and returns a default, which is also what lets it be proved safe.
  • A bounded model generates bounded code. The original model found a task's ancestors with four rounds of unrolling, enough for its four tasks and wrong for a fifth. Here the search folds over the task list, so it runs once per task however many there are.
  • A simulation bound written as a guard, such as "stop after day 6", would end up in the shipped code. Bounds belong in the values the simulator tries.
  • Random simulation reaches shallow states easily and deep ones rarely. A day-of reminder needed several clock ticks in a row; reachability searches now get twenty times the budget, which costs nothing when a witness exists.
  • The proof stage refused my own hand-written columnName, which called the proved function without establishing its precondition.

How much is proved

62 obligations are proved for all inputs. 82 hold across 10,000 simulated traces but Dafny cannot prove them unaided, mostly because they depend on folding over the warning list. The check reports the split and fails its proof stage until a person records that simulation is enough for them. I have deliberately not recorded that for the example: it is the owner's decision.

✗ proof     projects.ts: 12 proved, 12 not proved. …

That is close to where the application itself had settled: it proves its arithmetic kernel and model-checks the rest. Raising the proved share means writing the hard parts by hand with loop invariants, which the tools support but do not do for you.

What this says about 500,000 lines

The specs covered the rules of a 5,500-line application in about 700 lines, because Slack, HTTP and storage are not rules. A large codebase would be many such specs, one per area with a life cycle, with libraries beneath them. Some of what that needs is built and some is not:

  • Built: specs are checked in dependency order; proof cost is per spec; assurance is reported per obligation in three levels (proved, simulated and accepted, tested shell).
  • Built since: proof results are kept under a fingerprint of a spec's generated text and everything it imports, so only what changed is proved again; and a rule that spans two machines can be stated and proved in a machine built from a shared component.
  • Also built: a spec that passed simulation is not simulated again until it or something it imports changes. A repeat check of the three-spec example takes under two seconds.
  • Not built: two independent machines cannot observe each other; they have to be composed in a machine that holds both.
  • Not tried: anything near that size. The largest thing these tools have modelled is the 700 lines above.

Limits

  • The Quint subset is still a subset. Integers, booleans, strings, nested records, lists, sets of simple values, and sum types with or without data, so a state can carry only what is known at each stage. Not supported: maps, because a lookup of a missing key has no total translation (use a list of records with a key field), and recursion, which Quint itself does not have. Anything else is refused by name, never approximated. Each new operator is one case in the printer, but proofs over collections will need hand-written Dafny lemmas, which this toy does not exercise.
  • Half the obligations of a real model are simulated, not proved. The ledger makes that visible and stops it growing unnoticed; it does not make it smaller.
  • Rules across machines need a containing machine. A component (a library with a type, its guards and its functions) can be held twice in one machine's state, and that machine can state and prove a rule spanning both. Two independent machines still cannot observe each other.
  • One state machine per spec. Interacting machines, concurrency and time are where Quint is strongest, and the generated harness does not use that strength. A spec could opt out of the generated harness and bring its own actions.
  • Simulation samples. Event parameters are tried from −1 to 6. The proof covers all values for the always rules; quint verify can check the model exhaustively to a depth.
  • The generator is trusted between samples. Replay compares TypeScript with Quint on 50 simulated traces and every witness: every state, every law tried, and every event the model allowed or refused. It is a test of the generator, not a proof of it, and nothing short of proving the translator would change that.
  • Translation quality is the session agent's. The checks bound the damage, and the person signs off, but a rule that is wrong in both halves in the same way passes every check.
  • Unattended sync is weaker than a session. sync calls whatever command SPEC_AGENT names, and the quality of the rules it writes is that agent's. It has been run end to end only with a small local model. sync tries Claude Code first, but that CLI was signed out on the machine used, so that path has only been seen to fail over cleanly. The checks bound the damage: a wrong translation either fails a stage or waits in review for a person.
  • Agreement of prose and Quint is a judgement. The ledger records that the comparison was made. LemmaScript's claimcheck tool could add an automated second opinion.

The repository's README covers the process, AGENTS.md is the operating procedure for agents, and CONTRIBUTING.md is the reference for writing specs and using the generated code.
